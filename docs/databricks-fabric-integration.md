# Azure Databricks to Microsoft Fabric

## What is mirrored

Fabric's Azure Databricks integration is **metadata mirroring**. Fabric synchronizes selected Unity Catalog catalog, schema, and table structure and creates a corresponding Databricks-type shortcut for each supported table. The underlying Delta data remains in its source storage and is read through the shortcut. This is zero-copy access, not continuous physical replication into OneLake.

Microsoft explicitly distinguishes metadata mirroring from database mirroring in the [Fabric mirroring overview](https://learn.microsoft.com/en-us/fabric/mirroring/overview) and states that Databricks catalog data has no movement or replication in [Mirroring Azure Databricks Unity Catalog](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks).

Fabric also creates an autogenerated SQL analytics endpoint for the mirrored catalog. Supported tables can be queried with T-SQL and used by Power BI Direct Lake. Changes to the underlying data can take seconds to minutes to appear through Fabric; this POC does not claim an SLA.

## POC objects

The Databricks source uses a Premium workspace, Unity Catalog, a catalog/schema configured at deployment, and external Delta tables whose data remains in the dedicated ADLS Gen2 account:

- `transactions` — 500,000 deterministic initial rows by default;
- `transaction_risk` — one initial score per transaction;
- `merchants` — 5,000 deterministic merchants by default.

The seed notebook writes the `initial` source partition and enables Delta Change Data Feed. The incremental notebook adds transactions and a merchant and updates a deterministic group of risk scores. The Fabric mirrored catalog is intended to be named `databricks_bronze` and becomes the logical source-aligned Bronze layer.

## Prerequisites and authentication

According to the [configuration tutorial](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-tutorial):

1. Unity Catalog must be enabled.
2. External data access must be enabled on the metastore.
3. The connection identity needs `EXTERNAL USE SCHEMA` on the selected schema plus the Unity Catalog privileges needed to see the selected objects.
4. The Fabric connection can use an organizational account or service principal.
5. The source ADLS Gen2 storage must be accessible from Fabric. If it is firewalled, Fabric workspace identity and trusted workspace access are required.

The source connection credential is used for all catalog data queries. Do not embed an OAuth token, PAT, secret, or storage credential in the repository.

## Security consequence

Unity Catalog policies and permissions do **not** carry over to Fabric. [Microsoft's security guidance](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-security) requires Fabric permissions to be configured separately. It also notes that Unity Catalog RLS/column masks/ABAC aren't enforced when Fabric directly accesses the storage connection. Treat the mirror as a new authorization boundary and implement least privilege in Fabric.

## Current limitations relevant to this POC

Current [Databricks mirrored catalog limitations](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks-limitations) include:

- Fabric Runtime must be at least Spark 3.4 / Delta 2.4.
- The source ADLS Gen2 account must be accessible to Fabric.
- schema/table renames aren't supported for objects on inclusion or exclusion lists;
- tables with RLS/column-mask policies, lakehouse federated tables, Delta Sharing tables, streaming tables, views, and materialized views aren't supported;
- external tables that aren't Delta format aren't shown.

Empty schemas aren't shown. Metadata auto-sync covers schema/table additions and deletions when enabled; it is not a general replication of every Unity Catalog object or policy.

## Deployment and verification

Current evidence (2026-09-01): the Premium workspace and external Delta source tables are deployed; initial counts are verified; external data access is enabled; least-privilege service-principal grants are applied; and the Fabric mirror is running with automatic sync and three working shortcuts. The deterministic incremental job also succeeded and Fabric exposed 510,000 transactions, 510,000 risk rows, and 5,001 merchants.

Deployment verification sequence:

1. Confirm the Databricks seed job succeeded.
2. Run `validation/validate_databricks.py` in the Databricks environment and record counts.
3. Grant only the required Unity Catalog permissions.
4. In Fabric, create `databricks_bronze` as a Mirrored Azure Databricks catalog and select only the three tables.
5. Enable automatic metadata sync for the schema.
6. Verify each table shortcut and the SQL analytics endpoint.
7. Record source/Fabric counts and run the source-validation notebook.
8. Apply the Databricks incremental job, observe Fabric visibility, and record measured propagation time without converting it into an SLA.

Do not describe this integration as replicated, ingested, or copied. In diagrams and run evidence, label it `metadata sync + zero-copy shortcut`.
